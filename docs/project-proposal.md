## 1. Canvas 公布的项目要求

### 1.1 要做什么

老师要求：设计、构建、验证、维护一个**带 AI 组件的应用**。全程用 AI 编码代理写代码；人在关键节点监督、打断、批准。

> 📄 CS5351-2026-2027-project.pdf, p.1: "Design, build, verify, and maintain an AI-enabled software application using an AI coding agent under **auditable human supervision**."

应用自选，但必须满足两个硬条件：

1. **至少一个真正的 AI 组件**——CS5351-2026-2027-project.pdf, p.3 给了三个例子：LLM 功能、检索增强 RAG 流水线、AI 辅助决策路径
2. **至少一个安全相关边界**：AI 的输出必须被**确定性代码**（普通规则代码，非 AI）约束——AI 只能"建议"，最后拍板的必须是普通代码

> 📄 CS5351-2026-2027-project.pdf, p.3: "at least one genuine AI component ... and at least one safety-relevant boundary where the AI's output must be constrained by deterministic code."

**老师给的示范项目 VHIS**（一个保险理赔案例）：AI 组件对理赔申请给出建议（比如"这单可以赔"），但建议不能直接生效——必须先过**普通代码写的规则检查**（金额上限、黑名单、格式校验）。检查不过，AI 说的就不算数。学它的设计思想：AI 不拍板、规则代码把关。但**不能拿 VHIS 改改交差，题目必须自己做**。

> 📄 CS5351-2026-2027-project.pdf, p.3: "The reference implementation shown in lectures (VHIS) is **a pattern to follow, not a project to extend**."

**主题政策**：建议方向是增强 stock trading agent（github.com/tauricresearch/tradingagents），允许删改它的现有功能；或自选同等复杂度的题目。

### 1.3 怎么用 AI

**Agentic 软件工程红线**（cs5351-introduction.pptx, slide 20，逐字）：

- "AI-generated code is explicitly permitted and expected."
- "**No any non-agentic modification to the generated code is allowed or expected.**" —— 人工不得直接改 agent 生成的代码
- "Put all your 100% energy into specifying the control to the AI coding agent (**OpenCode**)" —— 全部评估基于 OpenCode
- "The full session transcripts are the **primary evidence of authentic human authorship**." —— 会话记录是"真是人做的"的主证据

一句话：**代码只能由 OpenCode 生成；人工只写规格、治理、需求等文档**。文件边界：`docs/` 与治理文件人工写；`src/`、`test/`、`prompts/`、CI 配置一律经 agent 会话改——手动改一行也算违规。查资料用的其他 AI（纯聊天、不进仓库）不需要留痕；**凡进入仓库的内容必须出自 OpenCode 并记入 ai-use-log**。

**教授讨论区澄清**：

- 用 tradingagents 当 baseline 可以，但**其现有代码不计入本组贡献**；D5 的 "from scratch" 指"agent 生成的实现组件"必须是我们自己的（2026-11-11）
- runtime policy（运行时策略）= gate 拦下错误之后"系统接下来采取什么决策与路径"（2026-11-13 公告）

**参考资源**：老师 11/13 刚发布 VHIS 完整参考实现 B3.1（460+ 测试、10 个 CI job、4 个 agent 配置）。使用边界：**只借鉴文档类型与 gate 模式；prompts、代码、测试用例一律自产**，防止被判"变相扩展 VHIS"。

> 📄 CS5351-2026-2027-project.pdf, p.3: "a pattern to follow, not a project to extend."

## 2. 项目主题（投票选一）

两个候选都满足 §1.1 的两个硬条件，都是同一个骨架：**AI 给建议，普通代码拍板**。

### 2.1 Topic A · ContentGuard——社区内容审核守卫

**这是什么**：一个给社区/论坛用的评论审核系统。用户发帖后，AI 审核 agent 先按社区政策给判定建议（比如"这条像人身攻击，建议拦截"）；然后**普通代码写的规则门复核**：命中违禁词表吗？超过误杀阈值吗？在白名单里吗？——复核通过才算数，最后决定放行、拦截还是转申诉。每条处置都留痕，用户可以申诉。

- **AI 组件**：三个 LLM 角色（初审 / 复议 / 申诉复核），判定时从政策库检索相关条款（RAG）
- **安全边界**：**"违规内容绝不直接放行"是零容忍规则**——AI 说放行不算数，规则复核通过才算

**选它爽在哪**：

- 最难拿的分现成：那道"改 prompt 必须重跑固定题库"的 CI 门（六道门里最难做的一道，§3.2 细讲），题库不用造——Kaggle 的 Jigsaw 数据集（真人标注的评论毒性数据，分六类）下载就能用
- 零容忍规则和"违反必失败"的测试信手拈来（违规零直通、处置全留痕、PII 不进日志）
- 架构修订素材天然：测试会暴露误判（尤其涉及身份的误杀）→ 第二轮设计加复核层——正好满足"流水线里要有一次基于测试证据的架构修订"
- 和 Assignment 完全不同领域，没有"像作业放大版"的包袱

**选它累在哪**：

- 社区政策文档要自己写：参考公开政策改写，不能直接搬真实平台的——政策写得糊，判定就糊，这份文档要花心思
- 题库以英文为主，中文演示场景要自己造一批小样本
- 答辩会被问"审核公平性"（误杀）——对策：用数据集里的身份偏见子集自测并写进报告，弱点变卖点
- demo 画面感中等：评论流 + 拦截提示，要靠准确率仪表盘撑场面

**复杂度够不够**：3 个 LLM 角色 + 政策库检索 + 一族规则门 + 评测管线——架构元素数跟"增强 tradingagents"同级，够辩护。

> 📄 题库来源：Jigsaw Toxic Comments（Kaggle 竞赛数据集）；业界审核评测综述：arxiv.org/html/2608.21775、promptfoo.dev/blog/top-llm-safety-bias-benchmarks

### 2.2 Topic B · CodeGuard——AI 代码审查守卫

**这是什么**：一个代码审查管线。提交代码后，AI 审查 agent 先找 bug 和安全漏洞（只是建议）；然后**普通代码写的扫描门复核**：用 Python 自带的 ast 模块（语法树分析）扫描——危险函数黑名单、硬编码密钥检测、有没有配套测试。AI 说的发现，过了扫描复核才进最终报告。

- **AI 组件**：审查 agent 找问题 + 从 CWE（安全漏洞的百科全书）检索同类案例（RAG）
- **安全边界**：**"AI 的发现必须过确定性复核才生效"**；危险 API 和硬编码密钥零容忍

**选它爽在哪**：

- 最难拿的分同样现成：Assignment 用过的 HumanEvalFix 164 题（每题带 bug 类型、故障特征）就是题库——评测管线还能参考 Assignment 代码改
- "降低 token 消耗"那个高分项（§3.3 高档次六条之一）是架构自带的：先用规则门把明显的筛掉，LLM 只看剩下的——这正是业界公认的做法（确定性检查可信，AI 审 AI 不可靠）
- 架构修订素材天然：AI 误报多 → 测试暴露 → 第二轮设计加预筛
- 答辩故事跟课程呼应：用课程教的"治理 AI"方法管 AI 写的代码

**选它累在哪**：

- 跟 Assignment 观感像（同领域 + 同题库）——要在开题时跟老师说清区别：作业是"单 agent 修 bug"，项目是"审查管线 + 门族 + 治理"；最好确认一句题库复用
- 商用工具已经很多（Copilot 等）——答辩口径：我们做的是治理与门体系，不是竞争审查算法
- ast 规则要自己设计：建议 8–12 条，每条配"违反必失败"的测试，太少撑不起复杂度
- AI 误报要先压住，不然 demo 全是误报——这恰好逼出"规则预筛"架构（卖点），但开发顺序必须先做门、后做 AI

**复杂度够不够**：3 个 LLM 角色 + CWE 检索 + 扫描门族 + 164 题评测管线。

> 📄 题库来源：HumanEvalFix（课程 Assignment 数据集，164 题）；方法论参考：deepsource.com/blog/ai-code-review-benchmarks（业界共识：确定性检查可信，AI 审 AI 是概率性的）

### 2.3 推荐

两案都是满分路线。投票时建议看三个问题：

1. **想写哪种规则门？**——A 的门是业务规则（违禁词表、阈值、复核流程）；B 的门是语法树扫描（ast 模块）。看组里人想写哪种
2. **想讲哪个故事？**——A 讲"平台内容的零容忍守卫和申诉闭环"；B 讲"用课程教的方法管 AI 代码"
3. **介不介意 B"像作业放大版"？**——介意就选 A

### 3.2 硬门槛（要求单明写，做到才有）

**六道 CI 拦截门，全部要在 GitHub Actions 里真跑**：

1. **测试批准门**——先批准测试，才允许写实现代码
2. **静态分析门**——代码风格、类型检查、依赖检查，每次提交都跑
3. **schema 门**——需求清单（YAML）要过格式校验
4. **语义评测门**——改 prompt 或换模型，必须重跑固定题库并达到质量阈值，不达标就拦
5. **回归门**——每次改动跑全部历史测试
6. **AI-use log 门**——改了代码却没更新 AI 使用日志的 PR，直接拦

> 📄 CS5351-2026-2027-project.pdf, p.10: 六道门 + 分支保护原文。

**分支保护**：CI 不绿不能合并；**只许 PR 合并、禁止直接 push 主分支**（这样提交历史才有意义——D7 明写"有意义的提交历史"）；安全关键路径的改动必须有人工审查 + 架构决策记录。

**测试覆盖规则**：每条验收标准至少 1 个测试；**每条零容忍不变式至少 1 条"违反必失败"的负向测试**；每个测试注明它验证的是哪条需求。

> 📄 CS5351-2026-2027-project.pdf, p.6: 测试覆盖规则原文。

## 4. 总工作量与五人分工

### 4.1 总量估算

约 **170–210 人时**（5 人 × 11 天 × 3–4h/天）。构成：文档工件 ~45% / 构建+测试 ~30% / CI 与仓库 ~10% / 视频·展示 ~15%。

**这个估算不依赖选题**：前三块是 D1–D9 的固定要求；构建部分两题同骨架（3 个 LLM 角色 + 规则门族 + RAG + 评测管线），只差各案的专有活（A 一份政策文档、B 一套 ast 规则，±10% 以内，归属见 4.2 表）。分工同理：D1–D9 是老师的固定清单，**今天就能认领，不用等定题**。

### 4.2 五人分工

每人四件套：**一条主线（D1–D9 的归属）+ 一条 OpenCode 会话记录（D5）+ 展示一个环节 + 一段自省（300–500 词）**。

**会话记录是满分主证据**（cs5351-introduction.pptx, slide 20），每条必须做实：一次真实开发任务——agent 先出计划、人批准后再写码（D9 要求）、构建、自验；**每个决策点（打断/批准/否决）标注理由，当天完成标注**。五条合起来覆盖六段流水线：需求分类 → 架构候选评估 → 计划批准 → 构建 → 验证合规 → 架构修订。时段交错并行、互不等待（测试框架 Sprint1 就开工，测试先行）。时点硬约束只有两个：需求第一版 15 号出（全队输入）；架构修订基于测试证据、**21 号 23:59 前完成**。

**主线分工**：

| 主线 | 负责的交付物 |
|---|---|
| **PM** | D6 Report 主笔（过程证据、自省汇总、>15 页图表统筹）、review-memo 模板+终审、工时贡献表、demo 视频、slides |
| **需求负责人** | D1 requirements.yaml + req-schema.json + schema 门（选 A：+政策文档） |
| **架构负责人** | D2 架构 11 份（多轮 ADD 主理）+ D9 Prompt.md + 应用侧 token 效率 |
| **治理与 CI 负责人** | D3 治理 6 份 + D7 CI 六门 + 分支保护 + README + ai-use-log 格式 + token 计量埋点 |

### 4.4 工时记录与风险应对

- **工时怎么算分**：平均线 = 总工时 ÷ 人数；你的权重 = 你的工时 ÷ 平均线（平均线即 1.0）；你的分 = 项目分 × 权重。示例（CS5351-2026-2027-project.pdf, p.7）：工时 60/55/35、项目 69 分 → 82.8/75.9/48.3。**总工时定平均线，你的工时定你在平均线上还是下**——多干被放大、少干被折损（极端情况有上下界，防搭便车）。表第一天建、每两天对一次；谁轻了补 Report 章节/视频剪辑/终检
