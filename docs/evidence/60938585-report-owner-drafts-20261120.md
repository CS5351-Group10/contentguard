## Architecture process contribution (§3.2 owner input)

ContentGuard's central architecture problem was how to use an LLM for moderation while preserving deterministic control over consequential decisions. The selected modular monolith assigns analysis an advisory role and gives policy the sole authority to authorize a transition. API coordinates these components, while escalation and audit participate in policy-owned persistence. This arrangement supports the five invariants without requiring distributed transactions or external platform mutations in the course build window. ADR-001 records the decision, and interface-contracts defines the data and failure boundaries.

The architecture evaluation distinguishes design judgment from experimental evidence. The initial ADD record compares three candidates with weighted criteria; its scores support the recorded decision but do not establish measured runtime superiority. A separate read-only OpenCode session on 19 November evaluated four choices in more detail: lexical versus embedding/hybrid retrieval, pinned versus mutable snapshots, deterministic versus model ranking, and deterministic compaction versus LLM summaries. Shiyi's recorded response retained all four recommended baselines. This later evaluation documents continued selection; it does not retroactively establish approval before the earlier implementation.

These choices address specific failure modes. Pinning snapshot identity and digest preserves historical attribution and detects tampering or a snapshot swap between retrieval and context assembly. Citation validation checks that returned references resolve to the supplied approved clauses. Whole-clause compaction avoids retaining a valid citation identifier beside truncated policy text, while trusted safety-capsule reinjection keeps authority constraints outside generated summaries. Retrieval failure produces typed failure evidence for policy to route safely, rather than a fabricated model verdict.

Implementation evidence has a narrower scope than the design. S3 merged in #52 as 397e002, with offline analysis contracts, provider fakes, context-budget and citation tests. The recorded 100-case synthetic retrieval set exercises expected matches and tampering/error conditions; it does not demonstrate live-model accuracy or comparative retrieval recall. The stage-2 evaluation also noted that concrete lexical ranking was supplied by a test fake and that production trusted-capsule wiring still needed integration verification. These remain meaningful acceptance questions rather than details hidden by a passing test count.

The trace matrix connects requirements to components and test evidence. Review of #72 updates merged S3 evidence while retaining explicit S2/S5 and live-provider gaps. This makes architecture documentation usable as an acceptance map: reviewers can distinguish implemented contracts, demonstrated behavior, planned work and deferred benchmarks. ## Architecture revision input (§3.5, to combine with Buna's S5 results)

The S5 narrative must begin with an executed observation, identify the architectural assumption it challenges, compare feasible changes and record the resulting human decision. Existing design evaluations and a strict Gate-4 configuration are useful prerequisites, but neither alone proves that a measured defect caused an architecture revision. Buna remains the owner of the final S5 execution and logbook; this owner input supplies the current architecture boundary and a concrete integration issue for evaluation.

The S2 draft #75 identifies a mismatch at the human-review boundary. The REST contract says a mandatory-rule-violating review request returns HTTP 422. The approved #51 plan further requires that such a request leave consequential state unchanged. In contrast, the current S1 engine's review path applies a mandatory reject floor and builds a reject decision; evaluate_and_commit can persist that result. This preserves rejection of prohibited content but does not preserve the no-write semantics of rejecting an invalid moderator request. Returning 422 after committing would also mislead the caller about the operation's effect.

Three options should be considered explicitly. Duplicating rule checks in API introduces a second authority and risks drift. Weakening the test to accept a committed reject changes the approved API behavior and requires a recorded requirements/contract decision. Keeping validation within policy and rejecting the disallowed request before the transaction preserves both a single authority and the existing contract, but requires a reviewed safety-critical S1 change with negative tests. The third is the architecture recommendation; it is not a claim that the change has been implemented or that a new execution plan has been approved.

The acceptance evidence should hold actor, case revision, pinned snapshot, review rationale and grants valid while varying only the requested outcome against the mandatory rule. A prohibited approval request must fail with unchanged case revision/status, queue contents and audit count. A permitted reject should still commit once; retries and stale revisions must retain their existing behavior. Fault cases must distinguish failed and unconfirmed persistence, and high-severity review requirements must remain binding. These checks belong to the policy boundary and real S2 adapter integration, rather than a stub that merely returns the expected HTTP status.

The final report should replace this pending-input paragraph with exact revision, command output, before/after defect evidence and reviewer decision once the owning sessions finish. Until then, this is a documented architectural finding and proposed resolution. It is not a completed S5 experiment, a live-provider benchmark, or release acceptance. ## §7 personal reflection — draft for Shiyi's confirmation

The most useful lesson I take from the architecture work is that a boundary must be expressed in data, persistence and review evidence before it can be trusted. Saying that an LLM is advisory is straightforward. Maintaining that position requires validated advisory DTOs, no enforcement capability in analysis, a policy-owned transaction, and responses that distinguish durable outcomes from uncertain ones. The ContentGuard architecture made these responsibilities explicit, and the implementation reviews showed why the details matter. A held case is not safely handed off merely because a function returns the word hold; the queue and audit record must actually be committed.

I also learned to distinguish the purpose of different evidence. Candidate scores explain a design judgment, offline fakes test contracts, and recorded semantic replay checks a particular artifact. None of these alone establishes production model quality. The later retrieval and context evaluation helped make this distinction concrete. Deterministic lexical retrieval, pinned snapshots and whole-clause compaction fit the project constraints, but retaining them does not prove that they outperform alternatives. Their reconsideration should be triggered by measured deficits and an agreed metric rather than by preference for a more elaborate technique.

The transcript work exposed a related documentation problem. A real S3 build record cannot substitute for an architecture-candidate evaluation simply because it occupies the canonical filename. Keeping the build evidence separately and identifying the later evaluation as later evidence produces a more defensible account. The same discipline applies to human intervention labels: a relayed automated instruction should not be counted as an additional personal decision, and a short recorded decision should not be expanded into invented dialogue.

For future work, I would make integration assumptions explicit earlier and review them using the complete operation rather than individual components. The S1/S2 mandatory-review mismatch illustrates this: enforcing a reject floor and rejecting an invalid review request are different behaviors, even though both prevent approval. Clarifying the expected transaction effect alongside the HTTP response would reduce late ambiguity. I would also keep the trace matrix synchronized as evidence lands and reserve sufficient time for real-provider and end-to-end verification. These are proposed lessons grounded in the recorded work; this draft awaits my confirmation before final personal attribution.
